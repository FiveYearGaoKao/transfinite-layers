# 性能

> 面向开发者。本文记录"价格/购买数量/生产链路"的性能模型、四条优化手段(P0~P3)与实测基线。
> 以【代码】为准,如有出入请修正本文档。

## 一、性能模型(优化前的成本从哪来)

一帧里最贵的两段是 `updateAutomations`(自动化)与 `updateLayers`(生产),两者共用同一批"价格/加成求值"。
优化前(真实存档 `v0.1.5`,9 个层级、c4 奖励 11 次、iu52 已购、总挑战完成数 90)的实测:

| 项目                                         | 优化前           |
| -------------------------------------------- | ---------------- |
| 单次价格求值 `dimensionCostAt`               | **43 ~ 49 µs**   |
| 其中 `softCapThreshold()`(c4 奖励 + ic4)     | 6.1 µs           |
| 其中 `softCapPower()`(iu52 + ic4)            | 19.6 µs          |
| 单次 `productionPerSecond`                   | 237 ~ 475 µs     |
| 其中 `applyTo('dimensionMult')`(13 个效果)  | 226 ~ 288 µs     |
| 一次"买最大"`maxBuyable` 的价格求值次数      | **112 ~ 114 次** |
| 整帧(存档原样)                               | 94.8 ms          |
| 整帧(点数顶到 1e10)                          | **404 ms**       |

两个关键结论:

1. **每次价格求值里约 30 µs 花在"与候选数量无关"的常量上**:软上限的阈值/幂次每次都要重解一遍效果管线。
2. **`maxSatisfying` 的高度域二分不随答案大小变化,恒为约 112 次求值**:它的设计目标是覆盖 `10^^1.79e308` 全值域,
   但在自动化里"每个物品每帧都付一次全值域代价"。点数在 1e10~1e100 量级时价格尚未越过软上限、
   答案落在小数量级,正好走"倍增 + 52 次高度二分 + 末段精修"这条最贵路径。

## 二、四条优化手段

### P0 帧内缓存(`compute/frameCache.ts`)

一帧内会被反复求值、但在本帧内不会变化的量,用 `frameCached(key, factory)` 只算一次。

已接入:

- **效果计划**(`compute/effects.ts` 的 `planFor`):本帧该数值点的"生效效果列表 + 折叠后的步骤",
  按 `数值点id|层级键|物品id` 缓存。一次价格求值原本要重解整条管线,现在只做算术。
  相邻同类 `static` 效果的折叠就在这一步里做(与注册顺序有关,与层级/物品/挑战状态无关)
- **所有槽位组合值**(`slotValue`)
- 曲线(`Curve`)解析后的参数(`compute/curves.ts`)
- **标了 `static: true` 的效果数值**(默认关闭,见下)

槽位组合值的缓存键是**具名槽位 id**(`defineSlot` 注册,全局唯一)+ 它的 `scope`,
不是对象引用、也不是 `slot.target`。原因有两个:

1. 槽位一旦允许在调用点临时构造,同一次价格求值就会各自造一个新对象,按对象身份作键必然 miss;
   故"同一个语义只有一个 id",按 id 作键既唯一又能命中。
2. 按 target 作键会让"两个语义共用一个 target"互相污染;不同语义必须拆成不同 id
   (价格软上限与维度生产软上限的参数就是两套:`priceCap:power` / `dimCap:power`)。

> **新增槽位时的约定**:必须经 `defineSlot` 具名注册且模块级唯一;**禁止在调用点临时构造槽位对象**。
> `scope` 按"值可能依赖什么"选:`'item'`(缺省,键 = 层级键|物品id)、`'layer'`(只依赖层级,键 = 层级键,
> 同层所有维度共用一份)、`'global'`(值与层级、物品都无关,键为空)。
> 声明 `'layer'`/`'global'` 就等于承诺值与物品id/层级无关,开发构建会用另一个上下文对撞校验。

### 效果数值的 static 标记与静态折叠

**效果自身的数值默认不进缓存**(dynamic)。标 `static: true` 的效果会进模板的**折叠段**,
在帧内物化计划时解析一次,并与同段(相邻同类型)的静态效果合并:连续 `add` 求和、连续 `mul` 求积、
连续 `exp` 幂次求积。于是 `dimensionMult` 的十来条乘法加成会合并成 1 步,只有真正的动态效果仍逐步求值。
段内成员可以被单独禁用(挑战禁用某个效果),合并时只累计**生效成员**——同类型可交换可结合,故这样合并是精确的。

- 标 `static` 是承诺:**只依赖购买/解锁/层级结构**(且不得读取 `current`,折叠段在物化时就取不到运行时值);
- 读**点数/维度数量(产出)/能量/时间/`bestPoints`/`resetTime`** 的效果必须保持 dynamic
  (它们在 `updateLayers` 内会变,缓存会让数值滞后一帧);
- 默认关闭的取向:漏标只是变慢,**不会算错**。

**开发构建会自动抓错标**:`clearFrameCache()` 会丢弃已记录的采样,而 `app/core.ts` 在
"生产阶段后"与"帧末"各调用一次 `runStaticSelfCheck`(绕过缓存重算并比对)。
前者抓"效果其实读了生产阶段会变的量",后者抓"某处写状态没清缓存"。报错会直接点名效果id与新旧值。

### 命中率与求值次数可观测

开发构建统计每一组缓存的**命中/未命中次数**(`compute/frameCache` 的 `cacheStats`)
与 `maxSatisfying` 的**搜索求值次数**(`tools/bisect` 的 `searchStats`),
调试模式下用 `/perf` 指令输出并清零。

判定"缓存/锚点到底有没有用"必须看这些计数,不看感觉。探针口径的实测(合成存档,一帧内):

| 场景                                     | 结果                                         |
| ---------------------------------------- | -------------------------------------------- |
| 一帧内 200 次维度价格求值 + 2 次"买最大" | `plan:dimensionCost` 命中 233 / **未命中 0** |
| 同帧内 20 次 `productionPerSecond`       | `plan:dimensionMult` 命中 20 / 未命中 0      |
| 同一个可购买做买最大 + 重复价格求值      | `plan:buyableCost` 命中 24 / 未命中 1        |
| 2 次买最大的搜索求值                     | 30 次(锚点失效、退化成通用搜索时约 112~114 次/次) |

真实存档(9 个层级、自动化全开)的典型计数:

```
plan:dimensionMult 命中0 未命中18256
slot:b11:base 命中0 未命中18256
plan:production 命中0 未命中18256
plan:dimensionCost 命中72022 未命中13040
plan:buyableCost 命中50903 未命中9780
base:ordinal 命中138297 未命中7448
slot:priceCap:base 命中10494 未命中5806
搜索求值 73452 次(计数已清零)
```

**怎么读这些数字**(命中率本身不是指标):

- `未命中 N 次` 只说明"这个键在本帧被首次求值了 N 次",**不等于有 N 次浪费**。真实存档里 `plan:dimensionMult`
  正是"9 层 × 4 维 = 36 次/帧,每个 (层级,物品) 各求值一次"——这种访问模式永远不可能命中,
  也不该命中;命中数只可能来自"同一帧内同一键被重复求值"(`maxBuyable` 的搜索/校验、UI 与逻辑各读一次)。
- 该看的是**同一个语义是否被不必要地重复求值**。典型信号:某个 `slot:` 的未命中次数 ≈ 层数 × 维度数,
  而它的值其实只依赖层级 —— 那就是 `scope` 标成了缺省的 `'item'`,应改成 `'layer'`
  (`b11:base`/`b11:amount`/`b13:amount` 已这样标注)。
- 帧内缓存的失效粒度是整代(`clearFrameCache()` 递增代次):一帧内每次购买都会清空一次,
  所以一帧内会有"购买次数"那么多个代次,跨代次的复用不存在。
- 判定优化是否有效看**整帧耗时**与这些计数的组合,不看命中率。

**契约(新增写状态时必须遵守)**:任何会改变上述值的写操作,都必须紧接着调用 `clearFrameCache()`。
目前调用点:`app/core.ts` 帧首、`logic/purchase.ts`(`buyItem`/`buyUpgrade`)、
`logic/reset.ts`(`doReset`/`resetData`)、`logic/infinity.ts`(`doInfinityReset`)、
`logic/challenges.ts`(`enterChallenge`/`exitChallenge`/`lockInvalidChallenges`)、
`logic/achievements.ts`(`unlockAchievement`)。
违反契约的后果只是同一帧内读到旧值(不会崩溃),但会造成数值不一致。

> 帧内缓存是"隐藏的跨调用状态",因此**新写状态必须检查这里**。
> 若将来出现"每帧内会变化的量被槽位读取"的新玩法(例如某个槽位读实时点数),该槽位就不能被缓存,
> 需要给它一个不走缓存的路径(或在变化处调用 `clearFrameCache()`)。

### P1 闭式求和与求逆(`compute/curves.ts` + `compute/buying.ts` + `tools/bisect.ts`)

价格与挑战目标都声明成一条 `Curve`(四个方法按需给,见 [effect机制.md](./effect机制.md) §六),
`compute/buying.ts` 只负责把"曲线 + 价格管道"组合成两条路:

- **求和** `sumCost(item, k)`:
  - 物品声明了 `sum`(常量/线性/几何/幂族)→ 用解析和。线性 `5+5n` 这类价格**必须**走这条:
    几何闭式对公比≈1的价格会高估约25%,导致"买最大"少买、约两成预算花不出去。
    线性/几何族直接用 `Decimal.sumArithmeticSeries`/`sumGeometricSeries`(与手写公式同源)。
  - 没声明 → 末两项几何闭式:`末项 · r/(r-1) · (1 - r^-k)`,只需 2 次价格求值。
    对公比恒定的价格(维度/加速器)是精确值;价格过软上限后公比可达 `10^63` 量级,末项主导同样精确。
    (不复用 `Decimal.sumGeometricSeries`:它要首项,而这里只有末两项,再往前要额外求值。)
- **求逆** `maxBuyable(item, budget)`:
  - 物品声明了 `sumInverse` → 解析解 `k`(线性/几何族用 `affordArithmeticSeries`/`affordGeometricSeries`,结果是向下取整的整数),
    再在锚点附近做**有界修正**(±8步);
  - 修正不收敛或没有锚点 → 退回通用搜索 `maxSatisfying`(锚点只影响迭代次数,不影响正确性)。
  - 带软上限的价格(维度/可购买)的锚点是 `priceCountAnchor`:预算 →(价格管道求逆)→ 未套软上限的原始价 →(曲线求逆)数量。
    价格过软上限后"每次只多买1个的相对增幅极大",故"整份预算都花在末项"是很好的乐观锚点。

**为什么解析锚点不能省**:`maxSatisfying` 的倍增找上界只有 `LOOP_CAP = 64` 次,即"一路可行"时最多只能探到 `2^64`。
答案超过 `2^64` 时(挑战目标在天文数字级资源下很常见)不带锚点会把答案截断在 `2^64` 附近;
补上锚点后返回真实值(实测:c1 在目标值 `10^(1e60)` 量级时,不带锚点返回 `1.8e19`=截断值,带锚点返回 `2.1e30`=解析解)。
因此**凡是能有解析逆/解析和的数值点都应把四件套声明齐**。

**精度口径**:求和只要求相对误差 <1%(常量/线性/几何精确,幂族是 Euler-Maclaurin 积分近似),
接口以 `node scripts/run-ts.mjs scripts/checkPricing.ts` 对撞逐项暴力相加为准。
`floored` 只把正向取整,和与逆不建模取整(取整造成的偏差远小于1%)。

**软上限的逆**:`softCapValue(x, m, 1/p, h)` 正是 `softCapValue(x, m, p, h)` 的逆。依据是幂运算的逆仍是幂运算,
且 `softCapValue` 内部本身会做 `height` 次 `layeradd10` 的还原。两个前提:

- **`p > 0` 即可逆**:阈值以下前向原样返回、阈值以上是幂函数,两者都严格单调,
  `p < 1` 时前向把数值"压小"、逆运算把它放大回去,同样成立。只有 `p <= 0` 时前向不是严格单调,信息才丢失。
- 往返**不是位相等**:`layeradd10` 在层1 的大 mag 下有约 1e-12 ~ 1e-10 的相对误差,判断"可逆"时用相对容差,不要用 `eq`。

`cap` 步骤的求逆由 `compute/effects.ts` 的 `invertAt` 统一处理(逆序折叠整条管道),
只在 `!p.gt(0)` 或值非有限/非正时返回 `undefined`,调用方退回通用搜索。

**维护约束**:物品价格公式或软上限参数变更时,只需改**曲线声明一处**;曲线与 `at`/`inverse` 必须成对声明。
估算失准只会退化性能,不会算错——这是"锚点 + 精确校验"相对"直接用解析式作答"的核心优势。

### 一个必须守住的边界:`maxSatisfying` 的第三参数是"原点",不是可行点

`tools/bisect.ts` 的契约是:求最大的 `k ≥ 0` 使 `g(k) = f(origin + k) ≤ budget`,返回的是**相对 origin 的增量**。
这里有三个必须同时成立的点,少一个就会出"买最大一个都不买"或"买最大买过头"的 bug:

1. **`f(origin + 0)` 才是恒可行的下界**(`sumCost(item, 0) = 0`),`f(origin)` 不是。
   `origin` 是"已购数"这个**原点偏移**,不是"一次买 origin 个"的可行性依据。
   例:层0维度已购 493、预算 1e1600 时 `f(493) = 10^3144`(不可行)、`f(1) = 10^853`(可行),
   正确答案是"还能买 196 个"——只有从 `k = 0` 起搜才能得到它。
2. **必须用倍增找上界,不能一次跳跃**。价格越过软上限后每多买 1 个的相对增幅可达 `1e14` 量级,
   可行计数集合可能窄到只有 1 个单位;任何一次性大跳(如取 `lo·2^64/64`)都会整段跃过这个窗口。
   倍增法逐个越过每个 `2` 的幂,必然落在真实窗口上。
3. **估算只用来缩小包围圈**。估算可行时把它当"更高的下界",估算不可行时把它当"不可行上界"
   (此时必须确认 `k = 0` 可行才可用它做包围圈),两种用法都保持严格正确。

> **增量口径只有一个换算点**:`maxCompletions` = 给定资源下的**增量**;`maxBatchCompletions` = 本次能增加的次数
> (唯一的对外口径),`exitChallenge` 用它结算、`challengeCard.vue` 用它显示;`sumCost(item, k)` 的 `k` 同样是增量。
> 校验必须包含:**已购数很大 + 预算相对较小**(软上限拐点附近)、**"只能买 1 个"**这种最窄的可行集合,
> 以及**所有调用方对返回值的解释**(增量 vs 绝对)都要跟契约对齐。

### P2 生产链路

`dimensionMult` 的 13 个效果里,`buyable-11` 与 `energy` 最贵,但它们读的都是槽位组合值;
给 `slotValue` 加上帧内缓存后,同一帧内同一层级的槽位只解一次。
同一帧内 `dimensionMultiplier` 会被 4 个维度各调一次,因此收益直接落在 `updateLayers` 上。

### P3 去掉 Decimal 的响应式代理

`player` 是 `reactive` 的,而**每一次** `player.x.add(y)` 都要先经过一层 Proxy;
Decimal 又是整体替换、从不就地修改的,这层代理没有任何语义。因此 `data/player.ts` 给
`Decimal.prototype` 打了 Vue 的跳过标记(`__v_skip`),运行期新建的 Decimal 同样不代理。

实测(真实存档、生产+自动化一帧、同一探针改动前后对撞,取 3 轮最佳):

| 构建 | Decimal 被代理 | 不代理 |
| ---- | -------------- | ------ |
| 开发构建 | 19.0 ms/帧 | **8.7 ~ 8.9 ms/帧** |
| 生产构建 | 24.6 ms/帧 | **10.0 ~ 12.4 ms/帧** |

两种模式下同一帧数的**游戏状态逐位相同**(点数/维度/已购/成就/知识/总时间)。
单机噪声较大(同一模式重复测量可差 2 倍),上表只保证量级;复现时用"同一进程内多轮取最佳 + 打印状态指纹"的口径。

前提与代价:**禁止就地修改 Decimal**(`normalize()`/`fromComponents()`/直接写 `.mag` 都会绕过响应式),
玩家可见数值的刷新靠**属性赋值**触发。

## 三、实测基线(真实存档,热机后,自动化全开)

真实存档口径:`v0.1.5` 存档,9 个层级、48 成就、21 个无限升级,层0点数 `1.3e1623`;开发构建(dev 计数会略增开销)。

| 场景                                 | 当前值                                    |
| ------------------------------------ | ----------------------------------------- |
| 整帧(生产 + 挑战惩罚 + 自动化)       | 中位 **9 ~ 10 ms**(P3 之前为 19 ~ 25 ms)  |
| `dimensionCostAt`(同代次重复读)      | 12.6 µs                                   |
| 一次 `maxBuyable`(维度,带解析锚点)   | **0.070 ms**                              |
| 一次 `maxBuyable`(可购买,带解析锚点) | **0.035 ms**                              |
| 同上但**不带锚点**(纯通用搜索)       | 0.193 ms(6 次求值)                        |
| 槽位组合值(开发构建,绕过缓存)        | `b11:base` 7 µs、`b13:amount` 4 µs、`b11:amount` 23 µs、`priceCap:power` 16 µs |

要点:

- **解析锚点让"买最大"不再走搜索**:维度与可购买的 `sumInverse` 命中后,`refineBySum` 只做常数次校验,
  实测搜索求值 **0 次/次**(不带锚点要走 6 次以上,答案更大时差距会拉大)。
- 一次价格求值里最贵的是曲线求值(`base.pow(...)`);`sumCost` 因此被设计成**恒定 2 次价格求值**
  (解析和支:首项+末项;几何闭式支:末项+前一项)。
- **独立于层级的槽位要用 `scope:'layer'`**:按"层级键|物品id"作键时,`b11:base`/`b11:amount` 会被
  同一层的 4 个维度各解一次(36 次/帧;9 个层级时其中 27 次是重复的),标成 `'layer'` 后变成
  未命中 9 次 + 命中 27 次每帧,整帧缓存命中率 65.8% → 72.2%。
- 生产链路的大头仍是 `updateAutomations` 与 `updateLayers`,要继续提速优先看这两段。

## 四、正确性验证方式

本项目没有测试框架,按以下方式验证(`npm run type-check && npm run lint && npm run build` 之外):

1. **对撞脚本**(放 `scripts/`,不参与构建;改动价格/曲线/效果管道时必须跑):

   ```sh
   node scripts/run-ts.mjs scripts/checkPricing.ts   # 曲线求和/和逆 vs 逐项暴力相加;maxBuyable vs 独立裁判(倍增+二分);
                                                     # 知识价格与player.base无关;线性价格"买最大"花光预算的回归
   node scripts/run-ts.mjs scripts/checkEffects.ts   # 折叠后的计划 vs 逐条求值;可逆数值点的求逆往返;
                                                     # 统计树由声明派生;跑一帧后static自检不得报警
   ```

   脚本会把开发构建的自检(`console.error`)也变成断言;存在真实存档时会自动载入以覆盖更多生效分支。

2. **求解器必须覆盖的用例**(已包含在脚本里,新增价格形状时要补):
   - **已购数很大 + 预算相对较小**(软上限拐点附近,最窄的可行窗口就在这里);
   - **"只能买 1 个"**(答案恰为 1,验证包围圈下界没有被跳过);
   - **锚点偏大 / 偏小 / 不可行**三种形态(锚点只影响迭代次数,结果必须与不带锚点时完全一致);
   - **数量级大到 Decimal 分辨不出 +1**(约 `1e16` 以上):只校验相对差,不校验"解+1 不可行"。
3. **主循环连跑数百帧**:不抛错、层级结构不变量(`checkLayerInvariants`)为空,
   且自动化把各维度推到该预算下的稳定值。
4. **性能探针**(构造存档、逐段计时、求值计数)不属于游戏代码,验证完即删;需要复现时按本文档的口径重建。
5. **缓存一致性**(新增写状态或 `static` 标记时):
   - 清空缓存前后重算同一个值必须相等;同一帧内两次读取必须是同一对象(命中缓存);
   - 走一次真实的写状态路径(进退挑战、解锁成就、购买)后,再读必须等于"清空缓存后重算"的值;
   - 新增 `static` 标记的效果要单独验证:标记前后**同一帧内的数值必须相等**
     (不相等说明它其实依赖了每帧变化的量,必须改回 dynamic);`checkEffects.ts` 里的
     "折叠 = 逐条求值"与 static 自检覆盖这一条。
