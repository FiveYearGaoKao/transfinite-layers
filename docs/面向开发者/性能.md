# 性能

> 面向开发者。本文记录"价格/购买数量/生产链路"的性能模型、三条优化手段与实测基线。
> 以【代码】为准,如有出入请修正本文档。

## 一、性能模型(优化前的成本从哪来)

一帧里最贵的两段是 `updateAutomations`(自动化)与 `updateLayers`(生产),两者共用同一批"价格/加成求值"。
优化前(真实存档 `v0.1.5`,9 个层级、c4 奖励 11 次、iu52 已购、总挑战完成数 90)的实测:

| 项目                                         | 优化前           |
| -------------------------------------------- | ---------------- |
| 单次价格求值 `dimensionCostAt`               | **43 ~ 49 µs**   |
| 其中 `softCapThreshold()`(c4 奖励 + ic4)     | 6.1 µs           |
| 其中 `softCapPower()`(iu52 + ic4)            | 19.6 µs          |
| 单次 `productionPerSecond`                   | 237 ~ 475 µs     |
| 其中 `calculate('dimensionMult')`(13 个效果) | 226 ~ 288 µs     |
| 一次"买最大"`maxBuyable` 的价格求值次数      | **112 ~ 114 次** |
| 整帧(存档原样)                               | 94.8 ms          |
| 整帧(点数顶到 1e10)                          | **404 ms**       |

两个关键结论:

1. **每次价格求值里约 30 µs 花在"与候选数量无关"的常量上**:软上限的阈值/幂次每次都要重解一遍效果管线。
2. **`maxSatisfying` 的高度域二分不随答案大小变化,恒为约 112 次求值**:它的设计目标是覆盖 `10^^1.79e308` 全值域,
   但在自动化里"每个物品每帧都付一次全值域代价"。点数在 1e10~1e100 量级时价格尚未越过软上限、
   答案落在小数量级,正好走"倍增 + 52 次高度二分 + 末段精修"这条最贵路径。

## 二、三条优化手段

### P0 帧内缓存(`compute/frameCache.ts`)

一帧内会被反复求值、但在本帧内不会变化的量,用 `frameCached(key, factory)` 只算一次。

已接入:

- `softCapThreshold()` / `softCapPower()`(阈值与幂次,含 c4/ic4/iu52 修饰)
- `dimSoftCapThreshold()` / `dimSoftCapPower()`(维度生产软上限)
- **所有槽位组合值**(`compute/effects.ts` 的 `slotValue`)

槽位组合值的缓存键是**槽位对象本身的引用**(`frameCachedByObject`,内部用 WeakMap + 代次作废),
不是 `slot.target`。原因:同一个子目标在不同调用点可以有不同的 `init` 基准值
(典型例子是 `softCap:power`:价格软上限的基准值 2 vs 维度生产软上限的基准值 0.75),
只按 target 作键会让两者互相污染。

> 由此得到一条**新增槽位时的约定**:被缓存的槽位应当是**模块级常量对象**
> (效果定义里的槽位、`compute/softCap.ts` 里的 `SLOT_*` 常量)。
> 若调用点每次都新建槽位对象,缓存不会命中(只是变慢,不会算错)。

**契约(新增写状态时必须遵守)**:任何会改变上述值的写操作,都必须紧接着调用 `clearFrameCache()`。
目前调用点:`app/core.ts` 帧首、`logic/purchase.ts`(`buyItem`/`buyUpgrade`)、
`logic/reset.ts`(`doReset`/`resetData`)、`logic/infinity.ts`(`doInfinityReset`)、
`logic/challenges.ts`(`enterChallenge`/`exitChallenge`/`lockInvalidChallenges`)、
`logic/achievements.ts`(`unlockAchievement`)。
违反契约的后果只是同一帧内读到旧值(不会崩溃),但会造成数值不一致。

> 帧内缓存是"隐藏的跨调用状态",因此**新写状态必须检查这里**。
> 若将来出现"每帧内会变化的量被槽位读取"的新玩法(例如某个槽位读实时点数),该槽位就不能被缓存,
> 需要给它一个不走缓存的路径(或在变化处调用 `clearFrameCache()`)。

### P1 闭式求逆(`tools/geometricSum.ts` + `compute/buying.ts` + `tools/bisect.ts`)

价格是几何级数(公比 `r = cost(n)/cost(n-1) > 1`)时:

- 总和有精确闭式:`sum = 末项 · r/(r-1) · (1 - r^-k)`,只需 2 次价格求值。
- "预算内最多买几个"可以反解:先把总预算折成末项预算 `budget·(r-1)/r`,再对价格公式求逆。

各物品族的求逆:

- 维度:`price = base^(a+b·n)`,未过软上限时代入 `log`;过了软上限则用
  `softCapInverse`(见下)把它解到未软上限的价格,再取 `log`。
- b11:`base^(n/2+1)`;b12:`10^(n(1+q·n)+c)`(对数域是二次式,取正根);b13:双重指数,由末项预算直接取对数。
- 求逆结果只当**搜索锚点**,`tools/bisect.ts` 的 `maxSatisfying` 会以它缩小包围圈,
  每步都用精确价格校验。因此**估算偏大或偏小都不会算错,只影响迭代次数**。

**软上限的逆**:`softCapValue(x, m, 1/p, h)` 正是 `softCapValue(x, m, p, h)` 的逆。依据是幂运算的逆仍是幂运算,
且 `softCapValue` 内部本身会做 `height` 次 `layeradd10` 的还原。两个前提:

- **`p > 0` 即可逆,不需要 `p > 1`**:阈值以下前向原样返回、阈值以上是幂函数,两者都严格单调,
  `p < 1` 时前向把数值"压小"、逆运算把它放大回去,同样成立。只有 `p <= 0` 时前向不是严格单调,信息才丢失。
- 往返**不是位相等**:`layeradd10` 在层1 的大 mag 下有约 1e-12 ~ 1e-10 的相对误差,判断"可逆"时用相对容差,不要用 `eq`。

因此 `compute/softCap.ts` 的 `softCapInverse` 只在 `!p.gt(0)` 或值非有限/非正时返回 `undefined`,调用方退回通用搜索。

**维护约束**:物品价格公式或其软上限参数变更时,必须同步检查对应的 `dimensionSumEstimate`/`buyableSumEstimate`。
估算失准只会退化性能,不会算错——这是"锚点 + 精确校验"相对"直接用解析式作答"的核心优势。

### 一个必须守住的边界:`maxSatisfying` 的第三参数是"原点",不是可行点

`tools/bisect.ts` 的契约是:求最大的 `k ≥ 0` 使 `g(k) = f(origin + k) ≤ budget`,返回的是**相对 origin 的增量**。
这里有三个必须同时成立的点,少一个就会出"买最大一个都不买"或"买最大买过头"的 bug:

1. **`f(origin + 0)` 才是恒可行的下界**(`sumCost(item, 0) = 0`),`f(origin)` 不是。
   `origin` 是"已购数"这个**原点偏移**,不是"一次买 origin 个"的可行性依据。
   例:层0维度已购 493、预算 1e1600 时 `f(493) = 10^3144`(不可行)、`f(1) = 10^853`(可行),
   正确答案是"还能买 196 个"——只有从 `k = 0` 起搜才能得到它。
2. **必须用倍增找上界,不能一次跳跃**。价格越过软上限后每多买 1 个的相对增幅可达 `1e14` 量级,
   可行计数集合可能窄到只有 1 个单位;任何一次性大跳(如取 `lo·2^64/64`)都会整段跃过这个窗口。
   倍增法逐个越过每个 `2` 的幂,必然落在真实窗口上。
3. **估算只用来缩小包围圈**。估算可行时把它当"更高的下界",估算不可行时把它当"不可行上界"
   (此时必须确认 `k = 0` 可行才可用它做包围圈),两种用法都保持严格正确。

> 回归教训(三轮都栽在同一个契约上):
>
> - 第一轮把 `start` 当可行点,`f(start)` 不可行就只向上倍增 → 返回 `start` → 表现为"买最大一个都不买"。
> - 第二轮改对了方向,但**把 `sumCost` 的"增量语义"当成了绝对计数**去传 `origin`(传成已购数),
>   于是 `g(k) = sumCost(item, 已购+k)` 变成了"再买(已购+k)个",答案被算成 0 或过大值。
> - 第三轮求解器改对了,但**调用方仍按旧语义解释返回值**:`logic/challenges.ts` 的 `exitChallenge`
>   过去写 `target = maxCompletions(...).add(1)`(旧语义下 maxCompletions 返回绝对次数),
>   改成增量语义后这句就变成"只多结算 1 次"——批量完成直接失效。
>   结论:**一次只需在一个地方换算**。现在挑战系统统一成:
>   `maxCompletions` = 给定资源下的增量;`maxBatchCompletions` = 本次能增加的次数(唯一的对外口径);
>   `exitChallenge` 结算它、`challengeCard.vue` 的按钮显示它,两边同源、不再各自加减。
>   (早期版本 `maxBatchCompletions` 返回"完成后的总次数",逼得 UI 做 `总次数 − 当前次数`、
>   逻辑侧做 `当前次数 + 增量`,两处约定必须同时记住,正是第三轮出错的土壤。)
>   校验必须包含:**已购数很大 + 预算相对较小**(软上限拐点附近)、**"只能买 1 个"**这种最窄的可行集合,
>   以及**所有调用方对返回值的解释**(增量 vs 绝对)都要跟契约对齐。

### P2 生产链路

`dimensionMult` 的 13 个效果里,`buyable-11` 与 `energy` 最贵,但它们读的都是槽位组合值;
给 `slotValue` 加上帧内缓存后,同一帧内同一层级的槽位只解一次。
同一帧内 `dimensionMultiplier` 会被 4 个维度各调一次,因此收益直接落在 `updateLayers` 上。

## 三、实测基线(真实存档,热机后,自动化全开)

> 注:早期几轮记录里的"优化后"数字不可直接比较——当时求解器有 bug,自动化每帧把 64 次循环跑满
> (约 3900 次价格求值/帧),而"性能分析对多帧取平均"把这段开销稀释了,造成"提升是假象"。
> 下表是修复求解器契约后的复测值。

| 场景                      | 优化前             | 优化后                      |
| ------------------------- | ------------------ | --------------------------- |
| 单次价格求值              | 43~49 µs           | 7.6~12.6 µs                 |
| `dimensionCostAt`         | 36.6 µs            | 12.5 µs                     |
| `updateLayers`            | 16.5~18.3 ms       | 11.2~12.8 ms                |
| `updateAutomations`       | 6.0 ms(旧存档原样) | 9.0~12.5 ms(自动化全开口径) |
| 整帧(存档原样,自动化全开) | 94.8 ms            | **20.4~22.4 ms**(中位)      |

修复求解器契约前的同一口径为 **243 ms/帧**(其中自动化 221~223 ms),修复后降到 20~22 ms:
收益来自"不再把 `LOOP_CAP` 跑满",而不是来自价格求值本身。

优化后逐段(真实存档,自动化全开):`updateAutomations` ≈ 9~12.5 ms + `updateLayers` ≈ 11~12.8 ms + 其余 0.3 ms。
后续要再提速,应优先看这两段(两者已接近,自动化仍是较大头)。

## 四、正确性验证方式

本项目没有测试套件,性能改动按以下方式验证(`npm run type-check && npm run lint && npm run build` 之外):

1. **求解器最大性校验**:对每个层级 × 每个物品 × 一组预算,断言"解可行"且"解+1 不可行",
   并与**暴力裁判**(从 `k=1` 逐个试到上限,取最大的可行 `k`)逐项对撞。三组用例必须都有:
   - **已购数很大 + 预算相对较小**(软上限拐点附近,最窄的可行窗口就在这里);
   - **"只能买 1 个"**(答案恰为 1,验证包围圈下界没有被跳过);
   - **估算偏大 / 偏小 / 不可行**三种形态(估算只影响迭代次数,结果必须与不带估算时完全一致)。
     用例要**每例重新载入存档**:跨用例复用状态会污染判定。
2. **合成用例**:`maxSatisfying` 也用纯函数对撞一遍——线性、几何、双层指数、
   极端斜率(每步 1e14)、全不可行、极大预算、`origin` 非 0 等。这能在不依赖存档的情况下锁住契约。
3. **缓存一致性**:
   - 清空缓存前后重算同一个值必须相等;
   - 同一帧内两次读取必须是同一对象(命中缓存);
   - **基准值不同的同名槽位不得互相污染**:按 `[默认, 0.75]`、`[0.75, 默认]` 等顺序各取一遍,
     结果必须与顺序无关;
   - 走一次真实的写状态路径(进退挑战、解锁成就)后,再读必须等于"清空缓存后重算"的值。
4. **主循环连跑数百帧**:不抛错、层级结构不变量(`checkLayerInvariants`)为空,
   且自动化把各维度推到该预算下的稳定值(不再每帧都走满循环上限)。

> 性能探针(构造存档、逐段计时、求值计数)不属于游戏代码,验证完即删;需要复现时按本文档的口径重建。
